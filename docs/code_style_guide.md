# 코드 스타일 가이드

## 1. 목적
이 문서는 `Gen_for_SmallBusiness` 프로젝트에서 코드를 작성할 때 지켜야 할 공통 규칙을 정리한 문서다. 이 프로젝트는 여러 생성 도구와 서비스 흐름이 연결되어 있기 때문에, 코드만 읽어도 흐름이 바로 이해되도록 작성해야 한다.

가독성, 일관성, 유지보수성을 최우선으로 한다. 특히 도구 호출 구조와 생성 파이프라인은 단계가 많기 때문에, 함수와 클래스의 역할을 코드 안에서 명확하게 드러내야 한다.

## 2. 기본 원칙
- 코드는 짧고 명확하게 작성한다.
- 한 함수는 하나의 역할만 맡는다.
- 이름만 보고도 역할이 어느 정도 드러나야 한다.
- 로직이 조금이라도 복잡하면 주석으로 의도를 설명한다.
- 추측이 필요한 코드는 허용하지 않는다.
- 나중에 처음 보는 사람이 읽어도 바로 이해할 수 있게 작성한다.

## 2-1. 절대 금지 규칙
- 규칙 기반 분기 로직으로 사용자 요청 의도를 판단하지 않는다.
- 키워드 매칭 표나 if/else 나열로 이미지, 영상, 음악 의도를 고르지 않는다.
- 요청 해석은 반드시 LLM 에이전트가 도구 호출로 수행한다.
- 생성 실패 시 폴백 결과물을 대신 반환하지 않는다.
- 모델이 실패하면 실패를 그대로 반환하고 원인을 드러낸다.
- "일단 대충 보여주기 위한 결과물"을 코드에 넣지 않는다.
- 문서에도 폴백 경로나 규칙 기반 판별을 허용하는 표현을 남기지 않는다.

## 3. 주석과 독스트링 규칙
### 3-1. 언어 규칙
- 모든 주석은 한국어로 작성한다.
- 모든 독스트링은 한국어로 작성한다.
- 영어만 던져두는 식의 짧은 주석은 금지한다.
- 외부 라이브러리 이름이나 모델 이름처럼 고유명사는 원문 그대로 둘 수 있다.

### 3-2. 주석 작성 원칙
- 주석은 "무엇을 하는지"보다 "왜 이렇게 하는지"를 설명해야 한다.
- 조건 분기, 예외 처리, 생성 단계 전환, 저장 규칙 같은 부분에는 주석을 꼼꼼하게 적는다.
- 나중에 버그가 생길 수 있는 지점은 반드시 주석으로 의도를 남긴다.
- 한눈에 이해되지 않는 계산, 정렬, 우선순위 선택 로직은 설명 주석을 추가한다.
- 도구 호출 순서가 중요한 곳은 호출 이유까지 적는다.

### 3-3. 금지하는 주석
- 코드만 봐도 아는 내용을 그대로 반복하는 주석
- 의미 없는 영어 한 줄 주석
- TODO만 남기고 설명이 없는 주석
- 현재 코드와 맞지 않는 오래된 주석

## 4. 함수 독스트링 규칙
모든 함수에는 아래 형식의 독스트링을 반드시 작성한다.

```python
def example_function(name: str, count: int) -> str:
    """
    함수 설명

    Args:
        name: 사용자 이름
        count: 반복 횟수

    Returns:
        생성된 결과 문자열
    """
```

### 4-1. 필수 규칙
- 모든 함수에 독스트링을 작성한다.
- 독스트링 첫 줄에는 함수가 하는 일을 한 문장으로 적는다.
- 인자가 있을 때만 `Args:` 섹션을 적는다.
- 반환값이 있을 때만 `Returns:` 섹션을 적는다.
- 인자나 반환값이 없으면 해당 섹션 자체를 쓰지 않는다.
- 예외 발생 가능성이 크면 본문 주석으로 이유를 보완한다.

### 4-2. 작성 예시
```python
def generate_copy(product_name: str, tone: str) -> dict[str, str]:
    """
    상품명과 분위기를 바탕으로 광고 문구 묶음을 생성한다.

    Args:
        product_name: 광고 문구를 만들 상품명
        tone: 문구에 반영할 전체 분위기

    Returns:
        메인 문구와 보조 문구가 담긴 딕셔너리
    """
```

```python
def save_project_assets(project_id: str, assets: list[str]) -> None:
    """
    생성된 결과물 파일 경로를 프로젝트 폴더에 저장한다.

    Args:
        project_id: 저장 대상 프로젝트 식별자
        assets: 저장할 결과물 경로 목록
    """
```

## 5. 함수 작성 규칙
- 함수 길이는 가능한 짧게 유지한다.
- 40줄이 넘어가면 분리 가능성을 먼저 검토한다.
- 조건문이 많아지면 보조 함수로 나눈다.
- 입력 검증, 모델 호출, 결과 저장은 한 함수에 섞지 않는다.
- 함수 이름은 동사로 시작한다.
- 불리언을 반환하는 함수는 `is_`, `has_`, `can_` 형태를 우선 사용한다.

## 6. 클래스 작성 규칙
- 클래스는 상태와 책임이 분명할 때만 만든다.
- 단순 데이터 묶음은 스키마나 데이터 클래스로 처리한다.
- 클래스 메서드에도 함수와 동일한 형식의 독스트링을 작성한다.
- 클래스 상단에는 이 클래스가 맡는 책임을 한국어 독스트링으로 적는다.

예시:

```python
class CopyGenerationService:
    """
    광고 문구 생성 요청을 처리하고 결과를 정리하는 서비스 클래스
    """
```

## 7. 파일 구성 규칙
한 파일 안에는 관련 있는 책임만 모은다.

권장 순서:
1. 모듈 독스트링
2. import
3. 상수
4. 데이터 구조
5. 핵심 함수 또는 클래스
6. 보조 함수

파일 상단에는 이 파일이 어떤 역할을 하는지 한국어 모듈 독스트링을 적는다.

예시:

```python
"""
문구 생성 도구와 결과 후처리 로직을 담은 모듈
"""
```

## 8. 주석을 특히 꼼꼼하게 적어야 하는 구간
아래 구간에는 반드시 충분한 설명 주석을 적는다.
- 오케스트레이터가 도구 호출 순서를 정하는 부분
- 입력 검증과 기본값 보정 부분
- 모델 프롬프트를 조합하는 부분
- 이미지가 있을 때와 없을 때 분기되는 부분
- 생성 경로가 분기되는 부분
- 파일 저장 경로를 정하는 부분
- 실패 재시도와 예외 처리 부분
- 관리자 로그와 상태값 저장 부분

## 9. 예외 처리 규칙
- `except Exception:`만 두고 끝내지 않는다.
- 왜 실패했는지 주석과 로그 메시지로 남긴다.
- 사용자에게 보여줄 메시지와 내부 디버깅 메시지를 구분한다.
- 예외 처리 블록에는 왜 이 예외를 여기서 잡는지 설명 주석을 적는다.

예시:

```python
try:
    result = generate_short_video(payload)
except TimeoutError:
    # 영상 생성은 시간이 오래 걸릴 수 있으므로, 시간 초과는 사용자에게 재시도 가능 상태로 보여준다.
    logger.warning("영상 생성 시간이 초과되었습니다.")
    raise
```

## 10. 로깅 규칙
- 주요 단계 시작과 종료는 로그로 남긴다.
- 어떤 도구가 실행됐는지 로그에 남긴다.
- 실패한 경우 입력 요약과 프로젝트 ID를 함께 남긴다.
- 민감한 원본 입력값은 그대로 로그에 남기지 않는다.

## 11. 네이밍 규칙
- 변수명은 의미가 드러나게 쓴다.
- `data`, `temp`, `result2` 같은 모호한 이름은 피한다.
- 파일명과 함수명은 소문자와 밑줄 기준으로 통일한다.
- 상수는 대문자와 밑줄을 사용한다.

좋은 예:
- `project_id`
- `selected_key_visual`
- `generated_banner_paths`
- `video_generation_payload`

나쁜 예:
- `d`
- `tmp`
- `x1`
- `res_final_new`

## 12. 프론트엔드 규칙
- 컴포넌트도 역할이 복잡하면 분리한다.
- 이벤트 핸들러 함수에도 독스트링 대신 바로 위 한국어 주석으로 역할을 설명한다.
- 화면 상태 분기는 JSX 안에 길게 늘어놓지 않고 별도 함수나 변수로 정리한다.
- 사용자에게 보이는 문구는 쉬운 한국어로 작성한다.

## 13. 백엔드 규칙
- API 라우터는 입력/출력만 담당하고, 실제 로직은 서비스나 도구 계층으로 분리한다.
- 도구 실행 로직은 `tools/`에 둔다.
- DB 저장 로직은 라우터에 직접 쓰지 않는다.
- 상태 변경 로직에는 반드시 설명 주석을 적는다.

## 14. 리뷰 기준
코드 리뷰 시 아래 항목을 확인한다.
- 모든 함수에 한국어 독스트링이 있는가
- 독스트링 형식이 `함수 설명 / 필요 시 Args: / 필요 시 Returns:`를 따르는가
- 주석이 충분한가
- 주석이 현재 코드와 맞는가
- 함수가 한 가지 역할만 하는가
- 도구 호출 흐름이 코드상에서 명확한가
- 예외 처리와 로그가 빠지지 않았는가

## 15. 결론
이 프로젝트는 생성 파이프라인이 길고 도구 호출 구조가 핵심이기 때문에, 코드 자체가 곧 문서처럼 읽혀야 한다. 따라서 모든 함수에 한국어 독스트링을 넣고, 주석도 꼼꼼하게 작성하는 것을 기본 규칙으로 삼는다.

특히 아래 규칙은 예외 없이 지킨다.
- 모든 함수에 한국어 독스트링 작성
- 독스트링 형식은 `함수 설명 / 필요 시 Args: / 필요 시 Returns:`
- 모든 주석은 한국어 작성
- 복잡한 로직에는 설명 주석을 꼼꼼하게 작성
